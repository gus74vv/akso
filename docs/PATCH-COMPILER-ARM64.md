# Patch compiler: native arm64 GCC 15.3 (2026-09-30)

> This closes the last x86 binary in the toolchain. The app itself was already
> native arm64 (Packr launcher + JRE + usb4java dylib); the missing piece was
> the patch compiler (`arm-none-eabi-g++`), which ran x86_64 under Rosetta.

## What changed

| | Before | After |
|---|---|---|
| Patch compiler | GCC 8-2019 (x86_64, **Rosetta**) | **GCC 15.3 (native arm64)** |
| Location | `external/gcc-arm/mac/gcc-arm-none-eabi-8-2019-q3-update/` | `external/gcc-arm/mac-arm64/` |
| Size | 441 MB | **280 MB** (pruned) |

**The board firmware is untouched, and so is the `axoloti.elf` the patch links
against (`--just-symbols`) → no reflashing needed.** The firmware stays the
same (**CRC 7072DEBF** at that time; the *current* firmware is **0x3238BAE5**,
see `STATUS.md`).

## Why: patch compilation happens on the Mac, not on the AKSO

A patch (`xpatch.cpp`, generated by the editor) is cross-compiled on the host
and uploaded to the board as ARM code; the STM32H7 only loads and runs it. A
natural proof: a patch stored as *startup* on the board boots in milliseconds,
while the same patch via *Live* took ~30 s — that time was the compile.

### Measurement (M1 Max, same `xpatch.cpp`, same flags)

| Toolchain | Execution | Compiling `xpatch.cpp` | Full pipeline (`make`) |
|---|---|---|---|
| GCC 8.3.1 (before) | x86_64 / Rosetta | 39.9–41.0 s | ~42 s |
| GCC 14.2.1 | native arm64 | 4.07–4.14 s | 4.51 s |
| **GCC 15.3.1** | **native arm64** | **3.64–3.70 s** | **4.15 s** |

Rosetta accounted for roughly 1.2×; the big win came from the GCC version jump.
Bonus: generated code is ~15–20 % smaller.

### Real breakdown of one "Live" run (GCC 15.3, 12,304-line patch)

| Stage | Time | Who |
|---|---|---|
| Compile | ~2.0 s | Mac |
| Upload sram1 (392 KB, USB FS) | ~0.5 s | USB |
| Upload sram3 | ~0.01 s | USB |
| DSP start + readback | ~0.2 s | Board |
| **TOTAL** | **~2.7 s** | |

## How the toolchain is selected

`Makefile.patch` (identical in the repo and both bundles):

```make
# Patch compiler: native arm64 (GCC 15.3) by default.
# Falls back to x86 GCC 8 (Rosetta) if its directory exists (rollback).
GCC_ARM64 ?= ${external}/gcc-arm/${platform}-arm64/bin
GCC_LEGACY ?= ${external}/gcc-arm/${platform}/gcc-arm-none-eabi-8-2019-q3-update/bin
gcc_bin ?= $(if $(wildcard $(GCC_ARM64)/arm-none-eabi-g++),$(GCC_ARM64),$(GCC_LEGACY))
```

- If `mac-arm64/` exists it is used (the normal case).
- Otherwise it falls back to x86 GCC 8.
- The `gcc_bin` environment variable still wins (`?=`).

## Rolling back

Everything needed for a rollback lives in
`~/Library/Akso/rollback-gcc8-20260930/`:

```
gcc-arm-none-eabi-8-2019-q3-update-mac-x86.tar.zst   # pruned x86 toolchain (37 MB)
Makefile.patch.backup/                               # the 3 original Makefile.patch files
xpatch.h.gch + xpatch.sram*.bin + SHA256SUMS.txt     # previous compiled state
```

### Option A — back to GCC 8 (x86/Rosetta)

```sh
G=~/Library/Akso/rollback-gcc8-20260930
B=/Applications/Akso.app/Contents/Resources/external/gcc-arm   # or the dev bundle
mkdir -p "$B/mac/gcc-arm-none-eabi-8-2019-q3-update"
tar --zstd -xf "$G/gcc-arm-none-eabi-8-2019-q3-update-mac-x86.tar.zst" \
    --strip-components=1 -C "$B/mac/gcc-arm-none-eabi-8-2019-q3-update"
mv "$B/mac-arm64" "$B/mac-arm64.off"     # so the Makefile falls back to x86
rm -f ~/Library/Akso/build/xpatch.h.gch  # the PCH is per GCC version
```

### Option B — force x86 without moving directories

Launch the app with the environment variable (the `?=` gives it priority):

```sh
gcc_bin="$B/mac/gcc-arm-none-eabi-8-2019-q3-update/bin" \
    /Applications/Akso.app/Contents/MacOS/Akso
```

### Option C — restore the original `Makefile.patch`

Copy from `$G/Makefile.patch.backup/` into the three places (repo + dev bundle +
installed bundle; original hash
`3dbb8d892c908c623c25750e4de2fb143f2e07e5e704045057dffc9982c2ea08`).

### What cannot be broken irreversibly

- The board firmware did not change → no brick risk; the ROM bootloader and DFU
  rescue path are always available.
- Patches are just files: if a patch built with GCC 15 misbehaves, revert the
  toolchain and rebuild.
- The repo is under git, so tracked parts can be reverted with
  `git revert` / `git checkout`.

## Notes

- The arm64 toolchain is **pruned**: it keeps only the
  `thumb/v7e-m+fp/hard` multilib (cortex-m7 hard-float) plus headers and
  binutils. It **cannot build the firmware**, nor any other architecture. The
  firmware still builds with the x86 toolchain (Rosetta) described in
  `ARM64-BUILD.md`.
- The x86 firmware toolchain **was removed from the working tree** of this repo
  to save space (it is still recoverable from upstream's history — see
  `README.md`). A pruned copy lives in
  `~/Library/Akso/rollback-gcc8-20260930/…-mac-x86.tar.zst` (204 MB
  extracted) and was verified to keep what the firmware needs (`libc_nano.a`,
  `libgcc.a`, `crt0.o`, `nano.specs`/`nosys.specs`). To build firmware: extract
  it and put its `bin` on `PATH`.
- Removed from the bundles: `gcc-arm/mac` (x86), and from the dev bundle also
  `gcc-arm/linux`, `gcc-arm/win` and `external/jdks` (build-only) — about
  2.4 GB less.
- Removed from the repo: `external/gcc-arm/{linux,win,mac}` (the `mac` one was
  x86) and `external/jdks/{linux_x64,mac_x64,win_x64}` (~1.5 GB less). The arm64
  toolchain lives in `external/gcc-arm/mac-arm64/` **untracked**
  (`.gitignore`), same as the extracted JDK: 280 MB of binaries do not belong in
  git. Note when rebuilding the bundle with packr: it copies `external/` as-is,
  so `mac-arm64/` must be present in the working tree.
- The new linker warning (`LOAD segment with RWX permissions`) is harmless: the
  patch is loaded into RAM by hand, not as an executable ELF.
